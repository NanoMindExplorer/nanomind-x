# Patches — change record for the nanomind-x engine

The twenty-one patches in this directory are the local modifications that were made
to the upstream 4.0.1 engine release. They are **already applied in-tree** in
`../engine/` — this directory is the change record, not an install step. The
old `apply.sh` (which re-applied them to a fresh `node_modules` install) was
retired with the fork; there is no `node_modules` engine to patch anymore.
Each v2.1.0 patch was verified 2026-11-06 to apply cleanly to the pristine
pre-v2.1.0 tree and reproduce the shipped file exactly (see the per-patch
notes below).

One patch text was rebranded with the fork: `2026-11-05-mcp-session-cookies.patch`
now reads the new session path (`~/.nanomind-x/cookies.json`); the change it
records is identical, only the path string changed.

Pristine pre-patch originals (`*.orig-2026-11-05`) are NOT shipped in this
repository; they live in the maintainer's local backup.

**Unblock retry (2026-11-06, v2.1.0) — no patch file, no code change.** The production `unblock` path (`_userRestAction` → signed SimpleHttp) was tested live on a sacrificial blocked account (@0xJiaming, blocked for the test, still blocked after): HTTP 404, same as v2.0. Four further genuinely different routes were tried on the same signed path and all 404d: `api.twitter.com/1.1/blocks/destroy.json` (user_id and screen_name), `x.com/i/api/1.1/blocks/destroy.json` with `screen_name`, and with the follow-style full param set. No GraphQL unblock mutation exists in the generated endpoint table or the discovery cache (only DM-scoped `dmBlockUser`/`dmUnblockUser`, which are not profile blocks). Conclusion: `blocks/destroy.json` is not served to this session on any host/param variant — a platform-side limitation, not a tool bug. A block stays effectively permanent from this tool; the current block list is @binanceminters, @0xJiaming, @fckfaster.
